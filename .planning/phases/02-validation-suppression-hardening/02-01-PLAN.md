  <action>
Create `src/validate/checkpoint.py` with:

1. `CheckpointError(Exception)` — raised on any validation failure.

2. `@dataclass CheckpointResult` — fields: phase (str), table (str), passed (bool), expected (int|None), actual (int|None), message (str).

3. `validate_row_count(df: pl.DataFrame, phase: str, table: str, expected: int, tolerance: float = 0.0) -> CheckpointResult`:
   - Computes actual = df.height, delta = actual - expected
   - If tolerance == 0.0: strict mode — any difference raises CheckpointError
   - If tolerance > 0.0: tolerance mode — raises only if abs(delta)/expected > tolerance
   - On failure: print structured log `[CHECKPOINT FAIL] phase={phase} table={table} expected={expected} got={actual} delta={delta}`, then raise CheckpointError with same message
   - On success: print `[CHECKPOINT PASS] phase={phase} table={table} rows={actual}`, return CheckpointResult(passed=True)

4. `validate_no_vanish(df: pl.DataFrame, phase: str, table: str, min_rows: int) -> CheckpointResult`:
   - Raises CheckpointError if df.height < min_rows (output lost rows vs input)
   - Structured log format on failure: `[CHECKPOINT FAIL] phase={phase} table={table} expected_min={min_rows} got={actual} delta={actual - min_rows}`
   - Success log: `[CHECKPOINT PASS] phase={phase} table={table} rows={actual} (>= {min_rows})`

5. `validate_schema(df: pl.DataFrame, phase: str, table: str, expected_columns: dict[str, type]) -> CheckpointResult`:
   - Checks that all expected columns exist in df.columns
   - Checks that column dtypes match expected (using Polars dtype comparison)
   - On missing column: `[CHECKPOINT FAIL] phase={phase} table={table} missing_columns=[col1, col2]`
   - On dtype mismatch: `[CHECKPOINT FAIL] phase={phase} table={table} dtype_mismatch={col: expected=X got=Y}`
   - Uses Polars native dtype checking (pl.Utf8, pl.Date, pl.Int8, etc.), NOT Pandera — keep Pandera as optional enhancement
   - On success: `[SCHEMA OK] phase={phase} table={table} columns={N} validated`

Note: Use Polars native dtype checking for the checkpoint module (simple, no new dependency required). Pandera schemas in schemas.py are for optional deeper validation.

Create `src/validate/schemas.py` with:

1. Module docstring explaining this defines expected schemas for critical PCORnet CDM tables using plain dicts (not Pandera) for checkpoint validation.

2. Schema dicts mapping column_name -> polars dtype for critical tables:
   - `DIAGNOSIS_EXPECTED`: ID (pl.String), ENCOUNTERID (pl.String), DX (pl.String), DX_TYPE (pl.String), DX_DATE (pl.Date or pl.String — accept either since date detection may vary)
   - `ENCOUNTER_EXPECTED`: ENCOUNTERID (pl.String), ID (pl.String), ADMIT_DATE (pl.Date or pl.String), ENC_TYPE (pl.String)
   - `ENROLLMENT_EXPECTED`: ID (pl.String), ENR_START_DATE (pl.Date or pl.String), ENR_END_DATE (pl.Date or pl.String)
   - `DEMOGRAPHIC_EXPECTED`: ID (pl.String), BIRTH_DATE (pl.Date or pl.String), SEX (pl.String), RACE (pl.String), HISPANIC (pl.String)

3. `CRITICAL_SCHEMAS: dict[str, dict]` mapping table name to its expected schema dict, e.g., `{"DIAGNOSIS": DIAGNOSIS_EXPECTED, "ENCOUNTER": ENCOUNTER_EXPECTED, ...}`

4. For each schema, use `strict=False` approach: only check that listed columns EXIST with correct dtype. Extra columns (flags, derived) are allowed.

5. Where a column may be either Date or String (depending on whether date detection succeeded), define as `(pl.Date, pl.String)` tuple and have checkpoint.validate_schema() accept either.

Design decision: Using plain Polars dtype dicts instead of Pandera for checkpoint validation. This avoids a new heavyweight dependency for what is essentially column-existence and dtype checking. Pandera in environment.yml is optional for future deep value validation (Phase 3). Add pandera to environment.yml as a commented-out optional dependency with a note.

Enhance `src/load/config.py` to add validation and startup summary:

1. Keep the existing `Paths` dataclass and `load_config()` function signature (backward compatible).

2. Add a new function `validate_config(paths: Paths) -> None` that:
   - Checks `paths.data_root.exists()` and `paths.data_root.is_dir()` — raise ValueError with clear message if not
   - Checks `paths.datastructure_path.exists()` and `paths.datastructure_path.is_file()` — raise ValueError if not
   - Checks `paths.valuesets_path.exists()` and `paths.valuesets_path.is_file()` — raise ValueError if not
   - Checks `paths.scratch_root` — if not exists, attempt `mkdir(parents=True, exist_ok=True)` (output dirs can be created)
   - Checks `paths.parquet_dir` — if not exists, attempt `mkdir(parents=True, exist_ok=True)`
   - Checks `paths.derived_dir` — if not exists, attempt `mkdir(parents=True, exist_ok=True)`
   - On any failure: print `[CONFIG FAIL] {field}={path} — {reason}` and raise ValueError
   - On success: print summary block:
     ```
     ============================================================
     CONFIG VALIDATION PASSED
     ============================================================
       data_root:          /path/to/data [OK]
       scratch_root:       /path/to/scratch [OK]
       datastructure:      /path/to/datastructure.txt [OK]
       valuesets:          /path/to/valuesets.csv [OK]
       parquet_dir:        /path/to/parquet [OK]
       derived_dir:        /path/to/derived [OK]
     ============================================================
     ```

3. Add a convenience function `load_and_validate_config(config_path: Path | None = None) -> Paths` that calls `load_config()` then `validate_config()` — this is what pipeline scripts will call instead of `load_config()` directly.

4. Do NOT use Pydantic — the existing dataclass + explicit validation is simpler and avoids adding a new runtime dependency. Research recommended Pydantic, but the existing Paths dataclass works well; adding Pydantic for 6 path checks is over-engineering. Document this choice in a code comment.

5. Update `environment.yml`:
   - Add a comment noting pandera and pydantic are available if needed for future phases
   - Do NOT add them as required dependencies (they're not needed for the plain-Polars checkpoint approach)

6. Add Google-style docstrings to all new functions following existing codebase conventions.
  </action>
