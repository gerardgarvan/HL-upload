  <name>Task 2 (T7): Document date parsing fallbacks</name>
  <files>.planning/docs/DATE_PARSING_FALLBACKS.md</files>
  <action>
Create .planning/docs/DATE_PARSING_FALLBACKS.md documenting:

1. **Supported formats (convert.py):**
   - SAS DATE9.: `%d%b%Y` (e.g., 01JAN2020)
   - SAS DATETIME: `%d%b%Y:%H:%M:%S` (e.g., 01JAN2020:14:30:00)
   - YYYYMMDD: `%Y%m%d` (only when column name heuristic matches; avoids false positives on 8-digit codes)
2. **Additional formats (dedup.py, quality_report.py, site_table.py):**
   - MM/DD/YYYY: `%m/%d/%Y` (TUMOR_REGISTRY, site_table date fallback)
3. **Detection:** Name heuristic (KNOWN_DATE_COLS or DATE_NAME_RE); value sampling; threshold 30% (name match) or 50% (value-only)
4. **>10% parse failure:** Column kept as string; convert_date_column returns action "kept_as_string" with reason
5. **Reference files:** src/load/convert.py (detect_date_columns, convert_date_column), src/clean/dedup.py (check_death_consistency)
</action>
  <verify>test -f .planning/docs/DATE_PARSING_FALLBACKS.md && grep -q "10%" .planning/docs/DATE_PARSING_FALLBACKS.md</verify>
  <done>DATE_PARSING_FALLBACKS.md exists with formats, detection logic, and >10% keep-as-string rule documented</done>
